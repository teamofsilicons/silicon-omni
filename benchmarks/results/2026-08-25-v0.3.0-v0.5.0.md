# silicon-omni 0.3.0 vs 0.5.0

Date: 2026-08-25 (Asia/Kolkata)

This is the grouped live workload from [`../grouped_live.py`](../grouped_live.py):
five Claude facts, five Codex facts, five Agy facts, then one exact fifteen-fact
Claude recall. Each version ran five times with a fresh `OMNI_HOME`, neutral work
directory, and session id. Version order alternated, no authentication preflight
ran, and every turn waited for both `END` and session idle.

Frozen provider configuration:

| Provider | CLI | Model | Effort |
| --- | --- | --- | --- |
| Claude | Claude Code 2.1.241 | `claude-haiku-4-5-20251001` | empty |
| Codex | codex-cli 0.149.1 | `gpt-6-astra` | `low` |
| Agy | agy 1.1.19 | `gemini-3.8-flash-low` | empty |

## Correctness and hotness

- Both versions passed 5/5 sessions and 80/80 turns.
- Every teaching reply was raw-exact `ACK`.
- Every final Claude reply was the exact compact JSON array: all fifteen facts,
  once each, in order.
- Provider routing and model selection were exact; there were no tool calls,
  fatal errors, or cleanup leaks.
- The provider PID and native conversation identity stayed unchanged throughout
  all five consecutive turns in all 15 provider groups for each version.
- Claude's native session survived the Codex/Agy round trip in 5/5 trials for
  each version. Its process was relaunched on return, which is an accepted
  provider-switch cost rather than a steady-turn restart.

## Complete-workflow latency

Lower is better. Delta is 0.5.0 relative to the paired 0.3.0 trial.

| Pair | 0.3.0 | 0.5.0 | Delta |
| --- | ---: | ---: | ---: |
| A | 49.543 s | 44.826 s | -9.5% |
| B | 54.657 s | 51.580 s | -5.6% |
| C | 52.878 s | 42.401 s | -19.8% |
| D | 45.552 s | 46.048 s | +1.1% |
| E | 42.829 s | 44.288 s | +3.4% |
| Median | 49.543 s | 44.826 s | **-9.5%** |
| Mean | 49.092 s | 45.829 s | **-6.6%** |

The median total for the fifteen teaching turns was 41.556 s on 0.3.0 and
37.571 s on 0.5.0 (-9.6%). The median final recall was 4.642 s and 4.948 s
respectively (+6.6%); that final provider/model response remained noisy.

## Provider activation vs hot turns

Each value is the median across five trials. “Hot” is each trial's median of
turns 2–5, followed by the median of those five values.

| Provider | 0.3 first | 0.3 hot | 0.5 first | 0.5 hot | 0.5 first/hot |
| --- | ---: | ---: | ---: | ---: | ---: |
| Claude | 2.708 s | 1.251 s | 2.663 s | 1.368 s | 1.95x |
| Codex | 4.056 s | 1.208 s | 3.288 s | 1.184 s | 2.78x |
| Agy | 14.248 s | 1.808 s | 13.727 s | 1.940 s | 7.08x |

The stable PID/native identity is the decisive hotness signal. The remaining
roughly 1.2–1.9 seconds is provider inference for a tiny `ACK`, not a process
boot. Across versions, hot-turn medians changed by +9.3% for Claude, -2.0% for
Codex, and +7.3% for Agy; those mixed directions are consistent with provider
latency noise rather than a framework-wide inference-speed change.

The public Python `send()` call itself had a 0.033 ms median on 0.3.0 and a
10.801 ms median on 0.5.0. These are different acknowledgement contracts:
0.3.0 enqueues in-process, while 0.5.0 crosses daemon IPC and returns only after
the message is durably journaled. 0.5.0's roughly 11 ms local acceptance path is
small relative to inference and no longer performs repeated open/chmod/tail
validation for every event.

These are descriptive results from five live trials, not a claim that cloud
latency moved permanently. Re-run the harness with the same frozen inputs when
provider CLI/model versions change.
